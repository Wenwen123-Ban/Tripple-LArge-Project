## 17.4 Notification Lifecycle

1. Creation event inserts row(s) into `notifications`, `user_notifications`, or `admin_notifications`. ✅ [VERIFIED FROM: src/api/transactions.py:207-238, src/api/transactions.py:305-322, src/api/transactions.py:407-436]
2. Admin frontend polls `/admin/notifications/` and uses returned `unread_count`. ✅ [VERIFIED FROM: scripts/admin/shared_init.js:130-226]
3. Student frontend loads `/api/user/notifications?filter=...` and renders grouped cards. ✅ [VERIFIED FROM: scripts/user/notifications.js:197-244]
4. Read marking updates `is_read=1`. ✅ [VERIFIED FROM: src/api/admin.py:658-680; src/api/users.py:557-575]
5. Used marking is applied when finalizing admin deletion with `notif_id`. ✅ [VERIFIED FROM: src/api/admin.py:493-502]
6. Clear behavior deletes read admin notifications or read user notifications depending on table. ✅ [VERIFIED FROM: src/api/admin.py:682-716; src/api/users.py:544-555]
